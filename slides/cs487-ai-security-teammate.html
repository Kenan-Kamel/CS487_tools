Fuzzing: Fuzz4All (Xia et al., ICSE 2024) generates inputs for compilers, interpreters, and runtimes — 76 bugs in GCC/Clang/Go/javac. ChatAFL (Meng et al., NDSS 2024) uses the LLM to infer protocol grammars, then feeds them to a coverage-guided fuzzer. TitanFuzz (Deng et al., ISSTA 2023) generates programs to test DL libraries — 65 bugs in PyTorch/TensorFlow. Symbolic execution and taint analysis are emerging: LLMs select paths or label sources/sinks, but the tool still executes and the human still triages.

Fuzz4All: Xia, Wei, Zhang, ICSE 2024. The LLM replaces the hand-written grammar that traditional grammar-based fuzzers need. Autoprompting: the LLM writes its own generation prompt from target documentation. ChatAFL: Meng, Nguyen, Le Goues, NDSS 2024. The LLM enriches the state machine that guides protocol fuzzing. The fuzzer still does execution and crash detection. Both papers: the LLM writes what the fuzzer needs to start; the fuzzer does what the LLM cannot (run millions of inputs, detect crashes, measure coverage).

TitanFuzz: Deng et al., ISSTA 2023. Two-stage: generate API-using programs from docs, then mutate. Some bugs are semantic (wrong numerical results), not just crashes. WhiteFox: Yang et al., ICSE 2024. White-box approach: the LLM sees the optimization code, not just the compiler's interface. Writes test programs that target specific assumptions. Pattern across all four papers: LLM writes the seed/grammar/test, tool executes, crash or coverage is the oracle, human triages. The LLM replaces manual specification, not the tool.

SPATA: path-sensitive typestate analysis for OS/kernel code. Typestate = finite-state protocol (e.g. lock → use → unlock). Path-sensitive = tracks states per execution path, not just per-function. No LLM. The point: traditional program analysis already finds real bugs. The LLM opportunity is in the manual parts — writing the specs and triaging the output — not in replacing the analysis engine.

Rice (1953): every non-trivial semantic property of programs is undecidable. "This patch preserves every intended behavior" is one. Al-Bataineh (ICSE 2026 NIER) spells it out for repair: no finite test-based oracle can establish patch correctness, so overfitting is structural, not a bug in the tool. Machines can prove "incorrect" with one counterexample, or "correct" for a bounded claim.
